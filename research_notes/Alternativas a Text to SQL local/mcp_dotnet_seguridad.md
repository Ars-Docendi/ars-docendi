## 1. Estado de la especificación MCP, transportes, autorización y gobernanza

### Takeaway
La revisión vigente ("latest") de MCP es **2026-07-28**, que vuelve el protocolo **stateless** (sin handshake `initialize` ni `Mcp-Session-Id`), mantiene stdio y Streamable HTTP como transportes y conserva una autorización basada en OAuth 2.1 + RFC 8707 + RFC 9728 con **prohibición explícita de token passthrough**. MCP está gobernado desde dic-2025 por la Agentic AI Foundation (Linux Foundation).

### Cited Findings
**Revisiones y fechas**
- El repo oficial contiene las revisiones `2024-11-05`, `2025-03-26`, `2025-06-18`, `2025-11-25` y `2026-07-28` (más `draft`); la navegación del sitio marca "Version 2026-07-28 (latest)" — [repo modelcontextprotocol/modelcontextprotocol, docs/specification y docs/docs.json](https://github.com/modelcontextprotocol/modelcontextprotocol/tree/main/docs/specification)
- 2025-11-25 (cambios vs 2025-06-18, vía buscador): discovery de authorization server con OpenID Connect Discovery 1.0; consentimiento incremental de scopes vía `WWW-Authenticate` (SEP-835); recomendación de OAuth Client ID Metadata Documents (SEP-991); íconos en tools/resources (SEP-973); guía de nombres de tools (SEP-986); elicitation en modo URL (SEP-1036); sampling con tool calling (SEP-1577) — [MCP changelog 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/changelog)
- 2026-07-28, cambios mayores (leído del changelog fuente): (1) se eliminan las sesiones de protocolo y el header `Mcp-Session-Id` de Streamable HTTP; el estado entre llamadas se pasa como "handles" explícitos en argumentos de tools (SEP-2567); (2) se elimina el handshake `initialize`/`initialized`: cada request lleva versión de protocolo y capacidades del cliente en `_meta` (SEP-2575); (3) nuevo RPC obligatorio `server/discover`; (4) `subscriptions/listen` reemplaza el GET SSE y `resources/subscribe`; (5) se eliminan `ping` y `logging/setLevel`; (6) "tasks" pasa a extensión oficial; (7) patrón Multi Round-Trip Requests (MRTR) reemplaza requests iniciados por el servidor (sampling, elicitation, roots); (9) se elimina la reanudación de streams SSE (`Last-Event-ID`) — [changelog 2026-07-28 (fuente)](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/changelog.mdx) / [versión web](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- 2026-07-28, cambios menores relevantes: servidores SHOULD devolver `tools/list` en **orden determinista** "to enable client-side caching and improve LLM prompt cache hit rates"; `ttlMs`/`cacheScope` obligatorios en resultados de listas; headers `Mcp-Method`/`Mcp-Name` obligatorios en POST; convenciones de propagación de trazas OpenTelemetry en `_meta` (SEP-414); `inputSchema`/`outputSchema` admiten cualquier keyword JSON Schema 2020-12; validación de `iss` (RFC 9207) obligatoria en clientes — [changelog 2026-07-28](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/changelog.mdx)
- 2026-07-28, deprecaciones: Roots, Sampling y Logging (SEP-2577); transporte HTTP+SSE (deprecado desde 2025-03-26) reclasificado formalmente como Deprecated; Dynamic Client Registration (RFC 7591) deprecado en favor de Client ID Metadata Documents; se adopta política de ciclo de vida con ventana mínima de deprecación de 12 meses (SEP-2596) — [changelog 2026-07-28](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/changelog.mdx)

**Transportes**
- Transportes estándar en 2026-07-28: `stdio` y `streamable-http` (directorio `basic/transports`) — [spec 2026-07-28 transports](https://github.com/modelcontextprotocol/modelcontextprotocol/tree/main/docs/specification/2026-07-28/basic/transports)

**Autorización (2026-07-28)**
- La autorización es OPCIONAL; las implementaciones HTTP SHOULD conformar la spec; las stdio "SHOULD NOT follow this specification, and instead retrieve credentials from the environment" — [authorization/index.mdx](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/basic/authorization/index.mdx)
- Base normativa: OAuth 2.1 (draft-ietf-oauth-v2-1-13), RFC 6750, RFC 8414, RFC 7591, **RFC 8707 (Resource Indicators)**, **RFC 9728 (Protected Resource Metadata)**, RFC 9207, Client ID Metadata Documents, OpenID Connect Discovery — [authorization/index.mdx](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/basic/authorization/index.mdx)
- Roles: el servidor MCP es un **OAuth 2.1 resource server**; el cliente MCP es un OAuth 2.1 client; el authorization server puede ser el mismo host o una entidad separada — [ídem](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/basic/authorization/index.mdx)
- Clientes MUST usar el parámetro `resource` (RFC 8707) con la URI canónica del servidor; servidores "MUST validate that access tokens were issued specifically for them as the intended audience"; "MCP servers MUST NOT accept or transit any other tokens"; tokens no van en query string; PKCE S256 obligatorio — [ídem](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/basic/authorization/index.mdx) y [security-considerations.mdx](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/basic/authorization/security-considerations.mdx)

**Gobernanza**
- El 9-dic-2025 Anthropic donó MCP a la **Agentic AI Foundation (AAIF)**, fondo dirigido de la Linux Foundation cofundado por Anthropic, Block y OpenAI, con apoyo de Google, Microsoft, AWS, Cloudflare y Bloomberg; proyectos fundacionales: MCP, goose y AGENTS.md; los proyectos mantienen control de su dirección técnica (vía buscador) — [MCP blog](https://blog.modelcontextprotocol.io/posts/2025-12-09-mcp-joins-agentic-ai-foundation/); [Anthropic](https://www.anthropic.com/news/donating-the-model-context-protocol-and-establishing-of-the-agentic-ai-foundation)
- Cifras de adopción declaradas por Anthropic/MCP (no verificadas independientemente): >10.000 servidores MCP públicos activos y >97 millones de descargas mensuales de SDKs — [Anthropic](https://www.anthropic.com/news/donating-the-model-context-protocol-and-establishing-of-the-agentic-ai-foundation)

### Inferences
- La revisión 2026-07-28 reduce bastante el costo operativo de un servidor MCP HTTP interno (sin sesiones en memoria ⇒ escalable detrás de un balanceador, encaja con un monolito ASP.NET Core sin estado).
- La autorización de MCP está pensada para **clientes de terceros** (Claude Desktop, VS Code, etc.) que descubren el AS y obtienen tokens con consentimiento del usuario. En un chatbot first-party donde el backend ya autentica al usuario, gran parte de esa maquinaria (discovery, CIMD/DCR) es irrelevante salvo que se quiera abrir el servidor a clientes externos.
- La spec cambia rápido (2 revisiones con cambios rompientes en ~8 meses, p.ej. elicitation de 2025-11-25 revertida en 2026-07-28): adoptar MCP implica seguir un estándar en movimiento.

## 2. Ruta de implementación en .NET y madurez (SDK C#, Microsoft.Extensions.AI, Agent Framework, convertidores OpenAPI, LLM local como cliente)

### Takeaway
El SDK oficial C# (`ModelContextProtocol`, `.Core`, `.AspNetCore`) es estable: **1.0** (feb/mar-2026), **2.0** alineado con la spec 2026-07-28 (28-jul-2026) y **2.2.0** como última versión (13-ago-2026). Se integra nativamente con `Microsoft.Extensions.AI`: las tools de un servidor MCP llegan al cliente como `AIFunction` y el **bucle agente lo corre el host** (`IChatClient` + `UseFunctionInvocation()`), contra cualquier endpoint OpenAI-compatible (llama-server/vLLM). Para exponer endpoints existentes hay atributos (`[McpServerTool]`) y convertidores OpenAPI de terceros inmaduros.

### Inferences
- Para Ars Docendi el host del agente sería el propio backend (o un servicio .NET): `IChatClient` apuntando a llama-server/vLLM vía el conector OpenAI de MEAI (o al conector de Anthropic), con `UseFunctionInvocation()`. Las tools pueden venir de (a) `AIFunctionFactory.Create(...)` sobre métodos C# in-process o (b) un `McpClient` contra un servidor MCP. El código del bucle es idéntico en ambos casos porque ambas fuentes producen `AIFunction`; por eso migrar de (a) a (b) más adelante es barato.
- Atención: llama-server/vLLM **no "hablan MCP"**; sólo hacen tool calling OpenAI-style. MCP es siempre una capa entre el host y el proveedor de tools; el LLM local no gana nada por sí mismo con MCP.
- Los convertidores OpenAPI→MCP producen mapeo 1:1 de endpoints, contrario a las buenas prácticas de diseño de tools (ver §6); son útiles para prototipos, no como diseño final.

## 3. MCP vs function calling in-process en un sistema cerrado first-party

### Takeaway
En un sistema cerrado con un único cliente (el chatbot propio), MCP no aporta capacidades al modelo: aporta **estandarización, reutilización por otros clientes (Claude Desktop, VS Code/Copilot, Claude Code) y un punto único de gobierno**. A cambio agrega un hop JSON-RPC, otra superficie de autenticación y una spec en movimiento. El consenso (mayormente opinión) es: empezar con function calling in-process y pasar a MCP cuando aparece un segundo cliente.

### Cited Findings
- Anthropic presenta MCP como solución al problema de integración N×M: "developers implement MCP once in their agent and it unlocks an entire ecosystem of integrations" — [Anthropic, Code execution with MCP (4-nov-2025)](https://www.anthropic.com/engineering/code-execution-with-mcp)
- Anthropic: "Most MCP clients load all tool definitions upfront directly into context"; con miles de tools los agentes "need to process hundreds of thousands of tokens before reading a request" — [ídem](https://www.anthropic.com/engineering/code-execution-with-mcp)
- Opinión recurrente en blogs (sin benchmarks controlados): para una sola app con pocas tools privadas, un servidor MCP "adds infrastructure for zero benefit"; envolver cada endpoint interno en MCP "because it is fashionable" es un anti-patrón; MCP se justifica cuando hay un segundo cliente/agente, equipos distintos dueños de tools, o descubrimiento dinámico; ventaja de gobierno: un gateway MCP ve todas las llamadas (vía buscador) — [Prefect](https://www.prefect.io/resources/mcp-vs-function-calling); [HackerNoon](https://hackernoon.com/when-you-dont-need-mcp-a-practical-guide-for-ai-developers); [Descope](https://www.descope.com/blog/post/mcp-vs-function-calling); [DEV](https://dev.to/moshe_io/mcp-vs-function-calling-a-practical-decision-framework-p78)
- Latencia por hop: algunas fuentes dicen "unos milisegundos" para un servidor local y otra 50–200 ms por llamada, pero esta última cifra no tiene sustento (vía buscador) — [Neuledge](https://neuledge.com/blog/2026-04-27/mcp-vs-function-calling); [Richard Pallangyo](https://www.richardpallangyo.com/tutorials/mcp-vs-direct-api)
- Simon Willison (opinión): MCP empeora el riesgo de inyección porque "encourages users to mix and match tools from different sources" — [simonwillison.net (GitHub MCP exploited, 26-may-2025)](https://simonwillison.net/2025/May/26/github-mcp-exploited/)
- Seguridad propia del protocolo: la spec de seguridad dedica secciones a confused deputy, token passthrough, SSRF, "State Handle Hijacking", compromiso de servidores locales, validación de URLs OAuth, mix-up, etc. — superficie que no existe en function calling in-process — [security_best_practices.mdx 2026-07-28](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/docs/2026-07-28/tutorials/security/security_best_practices.mdx)

### Inferences
- Para Ars Docendi (un único chatbot first-party, una GPU local, sin necesidad hoy de que Claude Desktop/VS Code consuman las tools) la opción de menor costo es **tools in-process como `AIFunction`** que invocan los servicios/contratos de los módulos (`Modules.X.Contracts`) con el `ClaimsPrincipal` del usuario. Esto respeta la regla del repo de no crear "abstracciones especulativas ni dependencias innecesarias".
- La latencia del hop MCP (local, ms) es despreciable frente a la latencia de inferencia de un 8B en una GPU compartida (segundos); el costo real de MCP es operativo y de seguridad, no de rendimiento.
- MCP se vuelve interesante si: (a) se quiere que docentes/administrativos usen las mismas tools desde Claude Desktop/Copilot, (b) otro sistema UNLaM necesita consumirlas, o (c) se separa el agente en otro servicio/proceso. Diseñar las tools como clases C# con `[McpServerTool]` **y** usarlas in-process (`McpServerTool`/`AIFunction` comparten el modelo de MEAI) deja la puerta abierta sin pagar el costo hoy.
- Comparado con Text-to-SQL, ambas variantes (MCP o in-process) reemplazan SQL generado por llamadas a operaciones controladas que reutilizan la autorización y los filtros de ámbito existentes; esa es la ganancia principal, independientemente de MCP.

- No encontré benchmarks controlados de latencia/overhead MCP vs in-process; las cifras disponibles son anecdóticas.

## 4. Autorización por usuario: identidad, token passthrough, OBO/token exchange, ámbitos y auditoría

### Takeaway
La spec prohíbe que un servidor MCP acepte o reenvíe tokens no emitidos para él (token passthrough). En .NET el SDK propaga el `ClaimsPrincipal` autenticado por ASP.NET Core a cada tool y soporta `[Authorize]` con filtrado de `tools/list`. Si el agente llama APIs aguas abajo con identidad del usuario, el patrón correcto es **token exchange (RFC 8693) u On-Behalf-Of**, no reenviar el token. Las reglas de negocio y filtros de ámbito deben seguir aplicándose en backend, nunca delegarse al LLM.

### Cited Findings
- "Token passthrough" = el servidor MCP acepta tokens del cliente sin validar que fueron emitidos *para él* y los pasa al API aguas abajo; está "explicitly forbidden"; riesgos: evasión de controles (rate limiting, validación), pérdida de trazabilidad/auditoría, ruptura de fronteras de confianza, servidor usado como proxy de exfiltración con tokens robados. Mitigación: "MCP servers MUST NOT accept any tokens that were not explicitly issued for the MCP server" — [security_best_practices.mdx §Token Passthrough](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/docs/2026-07-28/tutorials/security/security_best_practices.mdx)
- Confused deputy: servidores MCP que actúan como proxy OAuth hacia APIs de terceros con un client ID estático pueden saltear el consentimiento del usuario; la spec exige consentimiento por cliente — [ídem §Confused Deputy Problem](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/docs/2026-07-28/tutorials/security/security_best_practices.mdx); [security-considerations.mdx](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/basic/authorization/security-considerations.mdx)
- La spec incluye sección "Scope Minimization" (ataques, riesgos, mitigación, errores comunes) — [security_best_practices.mdx](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/docs/2026-07-28/tutorials/security/security_best_practices.mdx)
- SDK C#: el middleware de autenticación de ASP.NET Core llena `HttpContext.User`; el transporte copia el `ClaimsPrincipal` a cada mensaje; un parámetro `ClaimsPrincipal` en el método de la tool se inyecta automáticamente y **se excluye del JSON schema** ("clients never see it"); también disponible en filtros (`AddCallToolFilter`) para logging/auditoría — [identity.md](https://github.com/modelcontextprotocol/csharp-sdk/blob/main/docs/concepts/identity/identity.md)
- SDK C#: con `AddAuthorizationFilters()` se usan `[Authorize]`, `[Authorize(Roles=...)]`, `[AllowAnonymous]` en tools; si falla la autorización, en listas "Removes unauthorized items from the results" y en invocación devuelve error JSON-RPC de acceso prohibido — [identity.md](https://github.com/modelcontextprotocol/csharp-sdk/blob/main/docs/concepts/identity/identity.md)
- SDK C#: con stdio no hay autenticación; el `ClaimsPrincipal` es null salvo que se fije en un message filter desde el entorno del proceso — [identity.md](https://github.com/modelcontextprotocol/csharp-sdk/blob/main/docs/concepts/identity/identity.md)
- Sample `ProtectedMcpServer`: JWT Bearer, metadata de recurso OAuth (RFC 9728), `RequireAuthorization()` sobre el endpoint MCP — [samples/ProtectedMcpServer](https://github.com/modelcontextprotocol/csharp-sdk/tree/main/samples/ProtectedMcpServer)
- Token exchange / OBO (vía buscador, docs de gateways): el gateway/servidor intercambia el token entrante del usuario por uno con audiencia del servicio aguas abajo en cada llamada, de modo que el destino ve al usuario y no a un service principal compartido; RFC 8693 (Okta, Auth0, Keycloak) registra la cadena de actores en el claim `act`; Entra ID **no implementa RFC 8693**: su OBO es `jwt-bearer` con `requested_token_use=on_behalf_of` y exige que la audiencia del token entrante coincida con la app que intercambia — [agentgateway blog (12-jul-2026)](https://agentgateway.dev/blog/2026-07-12-agentgateway-token-exchange-jwt-assertion-entra-obo/); [Bifrost](https://docs.getbifrost.ai/mcp/auth/token-exchange); [Auth0 OBO](https://auth0.com/docs/secure/call-apis-on-users-behalf/on-behalf-of-token-exchange); [LiteLLM](https://docs.litellm.ai/docs/mcp_obo_auth)
- OWASP LLM06:2025 recomienda "Implement authorization in downstream systems rather than relying on an LLM to decide if an action is allowed or not" (vía buscador) — [OWASP LLM06:2025](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)

### Inferences
- Variante in-process (recomendada hoy): la tool recibe el `ClaimsPrincipal` del request HTTP del chat y llama al servicio de aplicación del módulo, que ya aplica permisos y filtros por ámbito (carrera/departamento) vía `IConsultasIdentity`. No hay token que propagar ni passthrough posible; el LLM nunca recibe el ID de usuario como argumento (debe venir del contexto, no del modelo).
- Variante MCP en el mismo backend: exponer `/mcp` con el mismo esquema JWT/cookie del sistema y tools con `ClaimsPrincipal` + `[Authorize]`; el host del chat (en el backend) llamaría al servidor MCP con un token **emitido para el recurso MCP** (audiencia propia), no reenviando el token de la SPA a otra API.
- Nunca usar una conexión/cuenta de servicio con privilegios amplios (el caso Supabase `service_role` de §5 es exactamente ese fallo); los filtros de ámbito deben estar en la consulta del backend, no en el prompt.
- Auditoría: un `CallToolFilter` (MCP) o un middleware sobre `FunctionInvokingChatClient` (in-process) permite registrar usuario, tool, argumentos saneados y resultado (sin PII en logs, según AGENTS.md), integrable con la infraestructura `audit` de `ArsDocendi.Shared`.

## 5. Riesgos de seguridad y mitigaciones (tool poisoning, inyección indirecta, lethal trifecta, rug pulls, excessive agency, CVEs)

### Takeaway
Los incidentes 2025–2026 muestran que el riesgo dominante no es el transporte sino la **combinación de datos privados + contenido no confiable + canal de salida** (lethal trifecta) y la confianza en servidores/descripciones de terceros. En un sistema first-party con tools propias, read-only y sin canales de salida, la superficie es mucho menor, pero la **inyección indirecta vía datos del sistema** (p.ej. texto libre cargado por usuarios) sigue aplicando y no tiene mitigación completa.

### Cited Findings
**Conceptos**
- Lethal trifecta (Simon Willison): acceso a datos privados + exposición a instrucciones maliciosas + capacidad de exfiltrar; GitHub MCP (may-2025): un issue público malicioso hizo que el agente filtrara información de repos privados; Invariant Labs lo calificó como problema arquitectónico, no bug del servidor; Willison: "we still don't have convincing mitigations" (vía buscador) — [simonwillison.net](https://simonwillison.net/2025/May/26/github-mcp-exploited/); [DevClass](https://devclass.com/2025/05/27/researchers-warn-of-prompt-injection-vulnerability-in-github-mcp-with-no-obvious-fix/)
- Supabase MCP + Cursor (~jul-2025): el agente operaba con `service_role` que evita Row Level Security; un ticket de soporte malicioso le ordenaba leer una tabla de tokens y escribirlos en un mensaje visible; Supabase recomienda modo read-only y acotado a proyecto, lo que elimina una pata de la trifecta (vía buscador) — [simonwillison.net](https://simonwillison.net/b/8820); [UpGuard](https://www.upguard.com/blog/ai-github-agents-issue-leaked-private-repos) (UpGuard data mal el origen del término; el post de Willison de mayo-2025 ya lo usaba)
- Tool poisoning (Invariant Labs, abr-2025): instrucciones ocultas en la descripción de una tool (ej. "add") que hacen leer claves SSH/config MCP y enviarlas en un parámetro; **tool shadowing**: un servidor malicioso altera el comportamiento respecto de tools de otro servidor confiable; **rug pull**: el servidor cambia definiciones después de aprobado (ej. CVE-2025-54136) (vía buscador) — [Invariant Labs](https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks); [CSA whitepaper (may-2026)](https://labs.cloudsecurityalliance.org/research-rb/csa-whitepaper-mcp-security-tool-poisoning-20260506-csa-styl/)
- CSA reporta tasas de éxito de ataque >60% en benchmarks sobre >45 servidores MCP reales y que OWASP clasificó tool poisoning como MCP03:2025 en su "MCP Top 10" (vía buscador; fuente secundaria, cifras no verificadas) — [CSA research note (jul-2026)](https://labs.cloudsecurityalliance.org/research/csa-research-note-mcp-tool-poisoning-ai-agent-exfiltration-2/)
- La spec exige que los clientes traten las tool annotations (p.ej. readOnly/destructive) como **no confiables** salvo que provengan de servidores confiables — [server/tools.mdx 2026-07-28](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/server/tools.mdx)

**CVEs e incidentes**
- CVE-2025-6514 (mcp-remote 0.0.5–0.1.15, corregido en 0.1.16): inyección de comandos del SO vía URL de authorization endpoint maliciosa en el flujo OAuth; CVSS 9.6; descubierto por JFrog; fuentes discrepan sobre explotación activa (vía buscador) — [JFrog](https://jfrog.com/blog/2025-6514-critical-mcp-remote-rce-vulnerability/); [SentinelOne](https://www.sentinelone.com/vulnerability-database/cve-2025-6514/)
- CVE-2025-49596 (MCP Inspector < 0.14.1): RCE por falta de autenticación entre cliente y proxy del Inspector, explotable desde el navegador (0.0.0.0/DNS rebinding/CSRF); CVSS 9.4; reportado 18-abr-2025, publicado 13-jun-2025 (vía buscador) — [Oligo Security](https://www.oligo.security/blog/critical-rce-vulnerability-in-anthropic-mcp-inspector-cve-2025-49596); [OSV](https://osv.dev/vulnerability/CVE-2025-49596)
- postmark-mcp (sep-2025, primer servidor MCP malicioso "in the wild"): paquete npm que suplantaba a Postmark; versiones 1.0.1–1.0.15 limpias, la 1.0.16 agregó una línea que copiaba en BCC todos los emails a un dominio del atacante; ~1.643 descargas (vía buscador) — [Snyk](https://snyk.io/blog/malicious-mcp-server-on-npm-postmark-mcp-harvests-emails/); [Postmark](https://postmarkapp.com/blog/information-regarding-malicious-postmark-mcp-package)
- La spec documenta además SSRF en discovery OAuth, compromiso de servidores MCP locales (binarios descargados con privilegios del usuario), hijacking de state handles, validación de URLs de autorización, mix-up attacks — [security_best_practices.mdx](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/docs/2026-07-28/tutorials/security/security_best_practices.mdx)

**Mitigaciones normativas**
- Spec tools: "there SHOULD always be a human in the loop with the ability to deny tool invocations"; servidores MUST validar inputs, implementar control de acceso, rate-limit y sanear outputs; clientes SHOULD pedir confirmación en operaciones sensibles, mostrar inputs antes de llamar y validar resultados antes de pasarlos al LLM — [server/tools.mdx](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/server/tools.mdx)
- OWASP LLM06:2025 Excessive Agency: causas = funcionalidad, permisos y autonomía excesivos; mitigaciones: minimizar extensiones disponibles, minimizar funcionalidad de cada una (p.ej. sólo lectura), autorización en sistemas aguas abajo, human-in-the-loop para acciones de alto impacto, ASVS/SAST/DAST (vía buscador) — [OWASP LLM06:2025](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)
- Controles comúnmente recomendados para MCP de terceros: allowlist de servidores, pinning por hash de definiciones de tools, tratar todo contenido devuelto por tools como hostil (vía buscador) — [CSA](https://labs.cloudsecurityalliance.org/research-rb/csa-whitepaper-mcp-security-tool-poisoning-20260506-csa-styl/)

### Inferences
- Tool poisoning, rug pulls, typosquatting y los CVEs listados afectan casi exclusivamente a **servidores/clientes de terceros o herramientas de desarrollo** (mcp-remote, Inspector, npm). Un servidor MCP propio, compilado en el monolito, sin cargar servidores externos, no hereda esos riesgos; tampoco las tools in-process.
- Lo que sí aplica a Ars Docendi: (1) **inyección indirecta** si las tools devuelven texto libre ingresado por usuarios (observaciones, descripciones de tareas, nombres) — tratarlo como dato, delimitarlo y no darle al agente acciones de escritura ni canales de salida; (2) **trifecta**: datos privados (PII) sí; contenido no confiable sí (texto libre); exfiltración — evitar tools que envíen emails, hagan fetch de URLs o generen links/markdown con imágenes remotas en el frontend; (3) **excessive agency**: empezar con tools read-only y, si hubiera escrituras, confirmación explícita del usuario en la UI y validación en backend.
- Comparado con Text-to-SQL, las tools acotadas reducen el riesgo de que el modelo lea tablas o columnas fuera de ámbito (no puede construir consultas arbitrarias), que es una mejora de seguridad sustantiva frente a la arquitectura actual.

## 6. Diseño de tools para agentes, tokens de definición y "code mode" con modelos pequeños

### Takeaway
Anthropic recomienda **pocas tools de nivel tarea** (no mapeo 1:1 de REST), nombres con namespacing, respuestas de alta señal con formato concise/detailed, paginación/truncado con defaults sensatos y errores accionables. Cada definición de tool consume contexto en cada request, lo que pesa mucho en un 8B local con KV cache compartido. "Code mode" reduce tokens drásticamente en catálogos grandes, pero exige sandbox y buena capacidad de programación: con pocas tools y un 8B no parece conveniente.

### Cited Findings
**Anthropic, "Writing effective tools for agents" (11-sep-2025)**
- "More tools don't always lead to better outcomes. A common error we've observed is tools that merely wrap existing software functionality or API endpoints"; recomendación: "building a few thoughtful tools targeting specific high-impact workflows" — [Anthropic](https://www.anthropic.com/engineering/writing-tools-for-agents)
- Consolidar: en vez de `list_users`, `list_events`, `create_event` → `schedule_event`; en vez de `get_customer_by_id`, `list_transactions`, `list_notes` → `get_customer_context`; preferir `search_contacts` a `list_contacts` — [ídem](https://www.anthropic.com/engineering/writing-tools-for-agents)
- "Too many tools or overlapping tools can also distract agents"; namespacing por servicio/recurso (`asana_projects_search`); prefijo vs sufijo tiene efectos "non-trivial" y dependientes del modelo — [ídem](https://www.anthropic.com/engineering/writing-tools-for-agents)
- Respuestas: devolver información de alta señal, evitar identificadores técnicos (uuid, mime_type); resolver UUIDs a nombres "significantly improves Claude's precision in retrieval tasks by reducing hallucinations"; parámetro `response_format` (`concise`/`detailed`), en su ejemplo la respuesta concisa usa ~1/3 de tokens (72 vs 206) — [ídem](https://www.anthropic.com/engineering/writing-tools-for-agents)
- Paginación, filtrado, truncado con defaults; Claude Code limita respuestas de tools a 25.000 tokens por defecto; errores con instrucciones específicas y accionables en lugar de códigos opacos o tracebacks — [ídem](https://www.anthropic.com/engineering/writing-tools-for-agents)
- Descripciones como para "a new hire"; parámetros sin ambigüedad (`user_id` en vez de `user`); modelos de datos estrictos; pequeñas mejoras de descripción "can yield dramatic improvements"; proceso guiado por evaluaciones con conjuntos held-out — [ídem](https://www.anthropic.com/engineering/writing-tools-for-agents)

**Costo de definiciones y code execution**
- Anthropic, "Code execution with MCP" (4-nov-2025): dos problemas — definiciones de tools que sobrecargan el contexto y resultados intermedios que pasan por el modelo (p.ej. +50.000 tokens por una transcripción copiada entre tools); presentando los servidores como API de código explorable en un filesystem, un caso bajó "from 150,000 tokens to 2,000 tokens—a time and cost saving of 98.7%" — [Anthropic](https://www.anthropic.com/engineering/code-execution-with-mcp)
- Mismo post: "Running agent-generated code requires a secure execution environment with appropriate sandboxing, resource limits, and monitoring. These infrastructure requirements add operational overhead and security considerations that direct tool calls avoid" — [ídem](https://www.anthropic.com/engineering/code-execution-with-mcp)
- Cloudflare "Code Mode" (26-sep-2025): convertir tools MCP en una API TypeScript tipada que el modelo programa y que corre en sandbox; tesis: los LLM son mejores escribiendo código que llamando tools porque vieron mucho más código real que tool calls sintéticos; reportan 1,17 M → ~1.000 tokens para una API de 2.500 endpoints (vía buscador; post original no accesible) — [Cloudflare](https://blog.cloudflare.com/code-mode/); [ContextBolt (secundaria)](https://contextbolt.com/blog/code-mode-mcp/)
- Afirmación secundaria: con menos de ~10 tools code mode es pérdida neta y la documentación de tool search de Anthropic recomienda tool calling directo por debajo de ese umbral (vía buscador, no verificado en la fuente) — [ContextBolt](https://contextbolt.com/blog/code-mode-mcp/)
- Spec 2026-07-28: orden determinista de `tools/list` para mejorar el hit rate de prompt cache — [changelog](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/changelog.mdx)

**Modelos locales pequeños**
- Evaluación de Docker (21 modelos, 3.570 tests): llama3.1:8B F16 0,835 y Q4_K_M 0,793; Qwen3 8B F1 0,933; fine-tunes especializados (Watt 8B, xLAM 8B) peor en parámetros/selección (vía buscador) — [Docker blog](https://www.docker.com/blog/local-llm-tool-calling-a-practical-evaluation/)
- ToolScan: modelos pequeños no ajustados para function calling (Llama3-8B) repiten llamadas a APIs pese a instrucciones contrarias — [arXiv 2411.13547](https://arxiv.org/pdf/2411.13547)
- Afirmaciones no medidas: más alucinación de nombres de función con modelos pequeños y muchas tools; cuantización agresiva del KV cache (q4_0) degradaría el tool calling (vía buscador) — [InsiderLLM](https://insiderllm.com/guides/function-calling-local-llms/); [XDA](https://www.xda-developers.com/biggest-local-llm-machine-useless-cant-call-single-tool-how-many-parameters/)
- Existen benchmarks deterministas ejecutables contra vLLM/llama.cpp (p.ej. Toolery, 143 escenarios) para medir localmente — [NVIDIA forums (Toolery)](https://forums.developer.nvidia.com/t/toolery-0-1-0-a-deterministic-tool-calling-benchmark-for-local-llms/371794)

### Inferences
- Para un 8B con varios usuarios concurrentes en una GPU, cada tool definida se reenvía en cada turno y ocupa KV cache por sesión; un catálogo 1:1 de endpoints (decenas de tools) degradaría tanto precisión como concurrencia. Conviene **5–10 tools de nivel tarea** por contexto (p.ej. `buscar_designaciones`, `resumen_docente`, `ocupacion_aulas`, `tareas_pendientes`), con filtros explícitos, paginación por defecto, `formato` concise/detailed y nombres legibles en lugar de IDs internos.
- Mantener las definiciones estables y en orden determinista favorece el prefix caching de vLLM/llama-server (mismo prefijo de prompt entre usuarios), lo que mitiga el costo de tokens de definición en una GPU compartida.
- Seleccionar tools por módulo/intención (router previo o filtrado por permisos del usuario, como hace `[Authorize]` en `tools/list`) reduce tokens y errores, y además evita mostrar al modelo operaciones que el usuario no puede ejecutar.
- Code mode no parece viable hoy para Ars Docendi: requiere sandbox de ejecución (nueva superficie de seguridad), su beneficio aparece con catálogos grandes, y no hay evidencia de que un 8B escriba código de orquestación fiable. Con un catálogo chico, tool calling directo es más simple y auditable (cada llamada es una operación con nombre revisable).
- Las tools deben devolver datos estructurados acotados por ámbito y con PII mínima necesaria; el resultado de una tool entra al contexto del modelo y, con Anthropic API, sale de la infraestructura local — decisión de privacidad a explicitar.

### Gaps
- No encontré benchmarks publicados que midan precisión de un 8B en función del número de tools (sweep de 5→50 tools); se sugiere medirlo localmente.
- No pude leer el post original de Cloudflare Code Mode ni evaluaciones independientes de code mode con modelos <10B.
- No verifiqué en documentación oficial de Anthropic el umbral "~10 tools" para tool search.
