## 1. Precisión composicional / multi-llamada: precisión por paso y cómo se compone el error (modelos chicos vs. frontera)

### Takeaway
En todos los benchmarks de llamadas encadenadas la precisión "de tarea completa" cae muy por debajo de la precisión "por llamada": con modelos frontera de 2024 se pasa de ~80 % por llamada a ~60 % de éxito total (ComplexFuncBench), ~28 % de secuencia exacta en NESTFUL y ~49 % en ToolHop; los modelos de 7–8B colapsan (5 % en ComplexFuncBench; 10–16 % en ToolHop; 0,5–36 % en BFCL multi-turno según categoría). El error compone aproximadamente como p^n y, peor, los fallos de argumentos (parámetros inventados) son silenciosos: la llamada se ejecuta y devuelve datos plausibles.

### Inferences
- Composición del error (aritmética, no de una fuente): si cada llamada correcta tiene probabilidad p y la tarea requiere n llamadas dependientes, P(éxito) ≈ p^n. ComplexFuncBench lo muestra empíricamente: GPT-4o 80,6 % por llamada → 60,5 % de tarea (consistente con ~2–3 llamadas efectivas); Qwen2.5-7B 18 % → 5 %. Con p = 0,9, tres llamadas dan 0,73; con p = 0,8, 0,51. Para un 8B local con p por llamada en el rango 0,2–0,6 (ComplexFuncBench, BFCL miss_param), cualquier pregunta que exija ≥2 llamadas encadenadas queda por debajo del 40 %.
- El dato más relevante para "respuestas incorrectas silenciosas" es miss_param: Qwen3-8B sin thinking pide el parámetro faltante sólo 4–13,5 % de las veces (según harness); el resto adivina. Un agente con tools REST completas no elimina esto: un `GET /designaciones?carrera=...` con la carrera adivinada devuelve filas reales y una respuesta perfectamente plausible.
- Los benchmarks de tool use son ruidosos (48 % de tareas defectuosas en BFCL según Epoch; discrepancias de 0,005 vs 0,155 entre harnesses), por lo que diferencias de pocos puntos no deben guiar la decisión; un golden set propio es imprescindible.

### Gaps
- No pude leer las tablas completas de NESTFUL (por modelo, incluido Granite/Llama 8B), ToolHop (Claude 3.5) ni Live API-Bench (por modelo y formulación); las cifras son de resúmenes.
- No encontré resultados de Seal-Tools, API-Bank ni StableToolBench con modelos 2025–2026 (son benchmarks 2023–2024 y en gran parte saturados/obsoletos); no los busqué en profundidad.
- No hay cifras oficiales actuales de BFCL multi-turno para Claude 4.x/Opus por categoría (sitio bloqueado).

## 2. Cuando la superficie de API se diseña para cobertura (endpoints de agregación, filtros, joins del lado servidor), ¿cuánto se acerca el tool calling a la precisión de una sola llamada? Tool gruesa tipo "query/semantic layer" vs. muchos endpoints finos

### Takeaway
La evidencia es indirecta pero consistente: reducir el número de llamadas y de tools visibles sube la precisión (Tool Search: 49→74 % en Opus 4; RAG-MCP: 13,6→43,1 % de selección; declarativo "un solo SQL con APIs como tablas virtuales" 68,9 % vs agente xLAM 35,7 %), y una capa semántica en forma *runtime* (consulta estructurada medidas/dimensiones/filtros compilada por el servidor) llega a ~100 % dentro de cobertura en benchmarks vendor. Pero incluso con la mejor superficie quedan dos errores de una sola llamada que no desaparecen: elegir mal la tool/métrica y llenar mal un argumento (filtro, período, entidad).

### Cited Findings
- **Anthropic, Tool Search Tool (nov. 2025)**: en evaluaciones MCP internas, exactitud 49 % → 74 % (Opus 4) y 79,5 % → 88,1 % (Opus 4.5) al cargar tools bajo demanda en vez de ~50+ definiciones (~72K tokens) — [Anthropic Engineering, Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use) (leído directo; sin detalle del set ni del n.º de tools)
- Mismo post: "The most common failures are wrong tool selection and incorrect parameters", sobre todo con nombres de tools similares; ejemplos de uso en la definición de la tool subieron la exactitud en manejo de parámetros complejos de 72 % a 90 % (test interno) — [Anthropic, Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)
- **Programmatic Tool Calling** (el modelo escribe código que orquesta tools y sólo devuelve el resultado final al contexto): recuperación de conocimiento interno 25,6 → 28,5 %; GIA 46,5 → 51,2 %; −37 % tokens — [Anthropic, Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)
- **Anthropic, Writing tools for agents**: "More tools don't always lead to better outcomes"; envolver cada endpoint como tool es un error común; recomienda tools consolidadas (`schedule_event`, `search_logs`), resolver UUIDs a lenguaje natural ("significantly improves Claude's precision in retrieval tasks by reducing hallucinations"), errores accionables y namespacing; sin cifras numéricas de consolidación — [Anthropic Engineering](https://www.anthropic.com/engineering/writing-tools-for-agents) (leído directo)
- **RAG-MCP (2025)**: al crecer el pool de MCP de 1 a 11.100, la selección correcta cae "markedly"; recuperar tools primero sube la selección de 13,62 % a 43,13 % y reduce >50 % los tokens del prompt — [arXiv 2505.03275](https://arxiv.org/html/2505.03275v1) [resumen]
- **LiveMCPBench (2025)**: 95 tareas sobre un ecosistema de miles de servidores; los errores de recuperación de tools explican casi la mitad de las fallas; Claude Sonnet 4 78,95 %, la mayoría de 12 modelos 30–50 %; corridas repetidas del mismo setup variaron entre 57,9 % y 76,8 % — [arXiv 2508.01780](https://arxiv.org/abs/2508.01780) [resumen]
- **Declarativo vs agéntico (IBM, EMNLP 2025 Industry)**: el LLM genera un único SQL donde las APIs son tablas virtuales que un reescritor reemplaza por UDFs; en el Benchmark II (Spider + APIs) 68,9 % vs 35,7 % del enfoque agéntico basado en xLAM — [arXiv 2510.16470](https://arxiv.org/abs/2510.16470); cifras sólo vía [Lacuna](https://lacuna.tiptreesystems.com/work/declarative-techniques-for-nl-queries-over-heterogeneous-data/wrk_3ee74bff820bfdc00b59210380726a98) [resumen secundario]
- **Capa semántica como tool** (patrón): el MCP de dbt expone `list_metrics`, `get_dimensions`, `query_metrics` (métricas + dimensiones + filtros); Cube describe "descubrir catálogo → pedido estructurado (medidas, dimensiones, filtros, rango temporal)" — [dbt, MCP server](https://docs.getdbt.com/blog/introducing-dbt-mcp-server); [Cube 2026](https://cube.dev/articles/semantic-layer-for-ai-agents-2026) [vendor]
- dbt 2026 (ya en notas previas): dentro de cobertura capa semántica 100 % vs Text-to-SQL 62,5 %; fuera de cobertura 0 % (devuelve error) vs 70 % — [dbt Labs 2026](https://docs.getdbt.com/blog/semantic-layer-vs-text-to-sql-2026) [vendor]
- **Cube, paired benchmark (abr. 2026; autor de Cube)**: 99 preguntas, Contoso Retail en ClickHouse, single-shot. Sólo esquema → esquema + documento semántico de 4 KB: Opus 4.7 50,5 → 67,7 %; Sonnet 4.6 46,5 → 68,7 %; GPT-5.4 45,5 → 68,7 % (McNemar p ≤ 0,0015). Con el documento, los tres modelos son estadísticamente indistinguibles; queda ~30 % de error residual. El paper distingue la forma *runtime* (corrección forzada al compilar la consulta) de la forma *contexto* (el modelo debe aplicar la semántica descrita) — [arXiv 2604.25149](https://arxiv.org/abs/2604.25149); [Cube blog](https://cube.dev/blog/why-semantic-layers-make-llm-analytics-reliable-a-paired-benchmark-across-three-frontier-models) [vendor, resumen]
- Agente NL2SQL mediado por capa semántica (2026, académico): >94 % en todas las clases de origen salvo Snowflake nativo 55,6 % (n = 18, alta varianza) — [arXiv 2606.31041](https://arxiv.org/html/2606.31041v1) [resumen]

### Inferences
- "Single-call accuracy" no es 100 %: es P(intent/tool correcta) × P(todos los argumentos correctos). Con tools gruesas bien descritas y pocas tools visibles, frontera parece estar en ~85–95 % (Tool Search Opus 4.5 88,1 %; ejemplos de uso 90 % en parámetros complejos); no hay cifras para 8B locales con superficie curada, pero BFCL miss_param y ComplexFuncBench sugieren que el término "argumentos correctos" es el punto débil de un 8B.
- Diseñar la API para cobertura convierte el problema de A en algo casi idéntico a B: una tool `consultar(medida, dimensiones, filtros, período)` es una capa semántica runtime; la diferencia restante entre A y B es *quién elige la tool y llena los slots* (LLM libre vs. router/slot-filling determinista con validación) y *qué pasa fuera de cobertura* (el agente improvisa composiciones vs. B cae a SQL con abstención o a "no sé").
- Riesgo propio de la tool gruesa: un filtro omitido no da error, da un número más grande (p. ej., contar designaciones de todas las carreras en lugar de una). Mitigación: parámetros obligatorios explícitos, eco de filtros aplicados en la respuesta, rechazo de combinaciones ambiguas.

### Gaps
- No encontré ningún benchmark que compare, con las mismas preguntas y el mismo modelo, "pocas tools gruesas de consulta" vs "muchos endpoints REST finos" (el punto más directamente relevante). La evidencia es por partes (cantidad de tools, consolidación, declarativo vs agéntico).
- No hay cifras de alucinación del paper de Cube (sólo pass rate) ni del paper GROUND (2608.26157), que define una taxonomía de alucinaciones en analítica y compara SQL directo vs capa semántica — [arXiv 2608.26157](https://arxiv.org/pdf/2608.26157) (sin números accesibles).

## 3. Híbridos, routers, cascadas y abstención: ¿cuál es el error medido del camino de fallback y cómo se evita que contamine la precisión global?

### Takeaway
La abstención estadística sobre Text-to-SQL funciona sólo a costa de mucha cobertura: las señales baratas (self-consistency, log-prob) tienen AUROC ~0,61–0,68 y no producen un subconjunto de bajo riesgo; un ensemble de verificadores (AUROC 0,82) permite, por ejemplo, contestar 27 % de las preguntas con 24 % de riesgo selectivo; abstención conformal en schema linking (RTS) da 98,9 % de exactitud *de linking* en lo no abstenido. Los híbridos que mejor protegen la precisión usan **abstención estructural** (lo no certificado no se puede expresar) para el camino principal y reservan la estadística para el fallback, con rotulado explícito; además, una cascada puede *dañar* respuestas (el fallback también falla), algo que las curvas riesgo-cobertura del primer modelo no capturan.

### Cited Findings
**Abstención y estimación de confianza en Text-to-SQL**
- **Selective-prediction study (2026)**: en un slice de BIRD, AUROC para predecir corrección: self-consistency por string 0,675; log-prob 0,669; estructural 0,619; por ejecución 0,613; relevancia de esquema 0,553; ejecutabilidad 0,500 (azar). Techo ~0,61–0,68 para señales estadísticas black-box; un ensemble de dos proveedores-juez llega a AUROC 0,82 (ECE 0,03) y permite, p. ej., **contestar 27 % con 24 % de riesgo selectivo**, mientras self-consistency "offers no valid low-risk subset". Verificadores fine-tuneados: ~0,77–0,79 in-distribution, ~0,66 en bases no vistas (cifra de reseña secundaria). Conclusión: no depender sólo de confianza por muestreo; incluir un componente que evalúe la lógica del SQL — [arXiv 2607.06799](https://arxiv.org/html/2607.06799v1); [Pith review](https://pith.science/paper/2607.06799) [resumen]
- En BIRD, log-prob no es mejor señal que el acuerdo entre muestras — [arXiv 2607.06799](https://arxiv.org/html/2607.06799v1) [resumen]
- **RTS (2025)**: predicción conformal sobre capas ocultas en la etapa de schema linking; si hay incertidumbre se abstiene y pide ayuda humana; 98,89 % de exactitud de linking en los casos no abstenidos en BIRD; abstenciones innecesarias ~5,3 % (tablas) y ~7,5 % (columnas) vs 12,77 % / 13,53 % de un baseline (contexto ambiguo en el snippet) — [arXiv 2501.10858](https://arxiv.org/html/2501.10858) [resumen]
- **RTS++ (EDBT 2026)**: conformal sobre el SQL final con "execution entropy" (agrupa candidatos por resultado); alta confianza → se ejecuta; baja → refinamiento o revisión experta; reporta 92,3 % (Spider) y 92,5 % (BIRD) de *exactitud selectiva* (sobre lo contestado). Otro snippet del mismo paper: abstención lleva la exactitud selectiva a 88,5 % y el feedback humano a 92,5 % (inconsistencia entre resúmenes; no se conoce la tasa de abstención) — [EDBT 2026, paper 177](https://openproceedings.org/2026/conf/edbt/paper-177.pdf) [resumen]
- Las garantías conformales dependen de intercambiabilidad calibración/test y del oráculo de ejecución que etiqueta la calibración (el riesgo "certificado" cambia según cómo se juzga correcto) — [arXiv 2609.25938](https://arxiv.org/html/2609.25938v1) [resumen]
- **TrustSQL** (2024, fuente antigua): las preguntas infactibles son 50 % del benchmark, por lo que "abstenerse siempre" obtiene RS = 50 sin riesgo; bajo penalizaciones altas ningún método superó consistentemente ese baseline; recomiendan generar sólo con alta confianza — [arXiv 2403.15879](https://arxiv.org/html/2403.15879v5) [resumen]
- **Detección de errores SQL**: SQLens combina señales de la base y del LLM y supera la mejor auto-evaluación LLM en +25,78 % F1 de detección; mejora EX hasta 20 % — [arXiv 2506.04494](https://arxiv.org/pdf/2506.04494) [resumen]. Testing metamórfico sin SQL de referencia: recall >89 %, precisión >54 % — [ResearchGate](https://www.researchgate.net/publication/399175418_Hallucination_Detection_for_LLM-based_Text-to-SQL_Generation_via_Two-Stage_Metamorphic_Testing) [resumen]
- Los errores semánticos complejos "typically result in empty query results without any error messages"; ErrorLLM sostiene que el self-debugging pierde eficacia porque los LLM modernos rara vez generan errores de ejecución explícitos — [ErrorLLM, arXiv 2603.03742](https://awesomepapers.io/ai-for-code/papers/2603.03742) [resumen]
- **Self-consistency por ejecución**: un coder 7B gana ~10 % con voto por resultados de ejecución (ganancias desde 3 muestras; 15 como buen trade-off) — [Query and Conquer (reseña)](https://www.themoonlight.io/review/query-and-conquer-execution-guided-sql-generation) [resumen secundario]; CSC-SQL: la respuesta más frecuente no siempre es la correcta y la brecha voto vs pass@k crece con más candidatos; +5,54 % sobre self-consistency estándar — [arXiv 2505.13271](https://arxiv.org/html/2505.13271v2) [resumen]; ReToolSQL: las consultas alucinadas tienden a quedar en clusters de tamaño 1 (sin evaluar como umbral de abstención) — [arXiv 2608.27796](https://arxiv.org/pdf/2608.27796) [resumen]
- Ruido en el oráculo: NL2SQL-BUGs halló errores semánticos en 106 SQL "gold" de BIRD dev (6,91 %) y 16 de Spider dev (1,55 %) — [NL2SQL-BUGs](https://nl2sql-bugs.github.io/) [resumen]

**Abstención estructural vs estadística**
- "Never the Number" (2026): distingue abstención estadística (generar y estimar si confiar: calibración, acuerdo de muestras, entropía, conformal) de estructural (las solicitudes sin forma autorizada no tienen respuesta expresable; no requiere estimar confianza); la cobertura queda fijada por las formas de pregunta autorizadas; propone combinar: estructural para lo inexpresable, estadística sobre un fallback generativo para lo expresable pero no anclado — [arXiv 2608.13926](https://arxiv.org/pdf/2608.13926) [resumen]
- AbstentionBench (NeurIPS 2025): el fine-tuning de razonamiento degrada la abstención 24 % en promedio — [mlanthology](https://mlanthology.org/neurips/2025/kirichenko2025neurips-abstentionbench) [resumen]

**Cascadas / routers / agentes que deberían abstenerse**
- Signed Rescue Routing (2026): rechazar e invocar otro predictor no es neutro: el modelo de fallback puede "rescatar" o "dañar"; la utilidad relevante es la diferencia condicional — [arXiv 2609.07786](https://arxiv.org/pdf/2609.07786) [resumen]
- UCCI (2026): las políticas heurísticas de abstención en cascadas no cumplen el riesgo objetivo por 7,5–12,5 %; proponen incertidumbre por margen de tokens + regresión isotónica — [arXiv 2605.18796](https://arxiv.org/html/2605.18796) [resumen]
- "Trust or Escalate" (ICLR 2025): jueces baratos primero y escalamiento con control de riesgo a partir de una tolerancia especificada — [ICLR 2025](https://proceedings.iclr.cc/paper_files/paper/2025/file/08dabd5345b37fffcbe335bd578b15a0-Paper-Conference.pdf) [resumen]
- AgentAbstain (2026): el mejor agente (Gemini 3.1 Pro) logra sólo 59,5 % de exactitud pareada en decidir cuándo no actuar; la capacidad de abstención es en gran parte independiente de la capacidad general — [arXiv 2607.10059](https://arxiv.org/pdf/2607.10059) [resumen]
- "When the Tool Decides" (2026): los agentes tienden a aceptar la salida de la tool "wholesale" — [arXiv 2606.14476](https://arxiv.org/pdf/2606.14476) [resumen]
- PRISMS (2026): steering condicionado al riesgo reduce el over-calling de 0,131 a 0,026 y sube la exactitud en tareas que requieren tool de 0,689 a 0,831 — [arXiv 2608.00218](https://arxiv.org/html/2608.00218) [resumen]

**Routers de intención**
- LLM vs NLU fine-tuneado (preprint 2026, CLINC150): recall out-of-scope Claude 85,6 vs RoBERTa fine-tuneado 58,1 vs TF-IDF 36,4, con exactitud in-scope comparable (empate estadístico, p = 0,24); el modelo fine-tuneado cae a 0 % cuando cambia el set de etiquetas; latencia p50 ~2,4 ms (RoBERTa local) vs 981 ms (API); recomiendan clasificador rápido + fallback LLM — [arXiv 2608.20371](https://arxiv.org/html/2608.20371) [resumen]
- EMNLP Findings 2025: prompts orientados a OOD suben el recall OOD hasta +21 puntos con caída similar o menor de F1 in-scope; enrutado BERT→LLM por incertidumbre — [ACL 2025.findings-emnlp.791](https://aclanthology.org/2025.findings-emnlp.791.pdf); [arXiv 2507.22289](https://arxiv.org/pdf/2507.22289) [resumen]
- Proyecto individual (no revisado): XLM-R-large con LoRA 94,2 % vs Claude Sonnet 4.6 85,3 % en BANKING77, 12 ms vs 2 s — [GitHub smallestbusiness/intent-router](https://github.com/smallestbusiness/intent-router) [anecdótico]

**Reutilización de consultas verificadas (de la ronda anterior)**: Genie marca "Trusted" sólo si se usa el asset exacto; Cortex usa verified queries como guía o como ground truth de evaluación — [Databricks Docs](https://docs.databricks.com/aws/en/genie/trusted-assets); [Snowflake Docs](https://docs.snowflake.com/user-guide/snowflake-cortex/cortex-analyst-evaluations) [vendor]

### Inferences
- Modelo de error del híbrido (B), derivado de lo anterior (inferencia): Error_total ≈ c_cert·(e_router→intent equivocado + e_slots) + c_fallback·r_fallback + e_render, donde c_cert y c_fallback son las fracciones de preguntas que van a cada camino y r_fallback es el riesgo selectivo del fallback *tras* abstención. Con consultas certificadas la consulta en sí aporta ~0 error; todo el error del camino certificado está en el router y en los slots, y ambos son verificables (eco de la interpretación, slots obligatorios, enums validados contra la base).
- El fallback Text-to-SQL de un 8B tiene hoy r ≈ 21 % sin abstención (7/33 en el set propio). La literatura no muestra una señal de confianza que lleve un generador de ~45–65 % de exactitud a riesgo <5 % sin perder la mayor parte de la cobertura (27 % de cobertura con 24 % de riesgo en el mejor ensemble). Por tanto, para "mínimas respuestas incorrectas", el fallback sólo es aceptable si (a) se rotula como no certificado, (b) muestra el SQL/interpretación, y (c) se abstiene ante desacuerdo de ejecución entre muestras; o directamente se desactiva y se responde "no puedo contestar con datos certificados".
- El router determinista es la pieza que impide que el fallback contamine: si el router manda a SQL preguntas que tenían intent certificado (falso negativo), se pierde precisión; si manda a un intent preguntas que no le corresponden (falso positivo), se producen respuestas incorrectas *certificadas*, el peor caso. El recall OOS del router (58–86 % en CLINC150) es el número a medir y optimizar; en duda, preferir "fuera de cobertura".
- En A (agente con tools), la "abstención" depende de que el LLM decida no actuar o preguntar: AgentAbstain (59,5 % del mejor modelo), BFCL miss_param (4–21 % Qwen3-8B; 53,5 % Haiku 4.5) y "When the Tool Decides" muestran que esa decisión es débil, sobre todo en modelos chicos. Esto es la diferencia estructural más importante entre A y B para silent wrong answers.

### Gaps
- No encontré mediciones publicadas de precisión global de un híbrido "router → consultas certificadas → Text-to-SQL con abstención" en producción (ni vendor ni académico) con tasas de error por camino.
- No hay cifras de riesgo-cobertura para Text-to-SQL con modelos 7–8B ni en español.
- La tasa de abstención de RTS++ y la cifra exacta (88,5 vs 92,5 %) no pudieron verificarse.

## 4. Modos de error multi-turno / conversacionales en cada arquitectura (arrastre de contexto, elipsis, correferencia)

### Takeaway
En ambas arquitecturas el multi-turno degrada la precisión, pero por razones distintas: en Text-to-SQL conversacional el error dominante es la resolución de contexto/ambigüedad y la acumulación al reescribir la consulta; en tool calling multi-turno, adivinar parámetros faltantes, perder estado y alucinar tools/argumentos cuando falta información. Ningún benchmark compara ambas sobre los mismos diálogos; el slot-filling determinista con estado explícito es, por diseño, el único que hace visibles estos errores.

### Cited Findings
- BIRD-Interact (ICLR 2026, de la ronda anterior): GPT-5 completa 8,67 % (c-Interact) y 17,00 % (a-Interact); la debilidad es la comunicación/aclaración, no la generación SQL — [arXiv 2510.05318](https://arxiv.org/pdf/2510.05318)
- CoSQL: dificultades de correferencia, elipsis, cambio de tema y seguimiento de qué elementos del esquema siguen relevantes; Track-SQL (NAACL 2025) gana +9,55 % EX en CoSQL al agregar módulos de seguimiento de esquema y contexto (+7,1 % en SParC); CoSQL tiene más diálogos ambiguos que SParC — [Track-SQL, NAACL 2025](https://aclanthology.org/2025.naacl-long.536.pdf) [resumen]
- CoE-SQL edita la consulta SQL incrementalmente en vez de reescribir la pregunta, "avoiding error accumulation caused by query rewriting" — [NAACL 2024](https://aclanthology.org/2024.naacl-long.361.pdf) [resumen; 2024]
- CoCodeS (CodeS-7B fine-tuneado con historia completa vs reescritura de pregunta con GPT, promediando pesos) supera cada variante por separado en CoSQL — [Future Internet 17(11):527](https://doi.org/10.3390/fi17110527) [resumen]
- En QA conversacional sobre KG: la elipsis suele resolverse con la interacción inmediata anterior, pero ningún modelo resolvió menciones a turnos no inmediatos — [arXiv 2301.12217](https://arxiv.org/pdf/2301.12217) [resumen; 2023]
- MTU-Bench (ICLR 2025, modelos 2024): todos los modelos rinden peor en multi-turno (M-S, M-M) que en single-turno; los errores de tool se concentran en los primeros turnos y luego suelen recuperarse — [MTU-Bench, ICLR 2025](https://proceedings.iclr.cc/paper_files/paper/2025/file/4d13b2d99519c5415661dad44ab7edcd-Paper-Conference.pdf) [resumen]
- ToolSandbox (Apple; NAACL Findings 2025): categoría "Insufficient Information" (falta la tool necesaria; el agente debe reconocer que no puede) con "minefields" que anulan la trayectoria; ejemplos: GPT-4 alucinó el timestamp actual y llamó `timestamp_diff`; GPT-3.5 alucinó una tool `remove_contact`; el desempeño en información insuficiente correlaciona negativamente con las otras categorías; GPT-4 y Claude-3-Opus rindieron peor que modelos medianos en dependencia de estado por llamadas paralelas erróneas — [ToolSandbox](https://aclanthology.org/2025.findings-naacl.65/); [resumen Medium](https://medium.com/@techsachin/toolsandbox-stateful-conversational-interactive-evaluation-benchmark-for-llm-agents-tool-use-932afc110b4b) [resumen]
- BFCL v3 multi-turno: Qwen3-8B miss_param 0,215 (thinking) / 0,040 (sin thinking); long_context 0,290 / 0,130 — [olmo-eval PR #449](https://github.com/allenai/olmo-eval/pull/449) [resumen]
- HammerBench: descompone el manejo de slots faltantes (detectar, decidir qué preguntar, formular, llamar); los modelos livianos no logran todas las habilidades a la vez — [arXiv 2412.16516](https://arxiv.org/html/2412.16516v1) [resumen]
- τ²-bench: pass^k cae al repetir la misma tarea (inconsistencia entre corridas) — [arXiv 2506.07982](https://arxiv.org/pdf/2506.07982) [resumen]

### Inferences
- En A, el error conversacional típico de Ars Docendi sería: "¿y en Ingeniería?" tras "¿cuántas designaciones pendientes hay en Económicas?" → el agente reutiliza o descarta filtros previos (estado, período) sin decirlo. En B con slot-filling, el estado de slots es un objeto explícito: el siguiente turno sólo sobrescribe `carrera`, y la respuesta puede eco-ar "Designaciones en estado Pendiente, período 2026-1, carrera Ingeniería". Esto convierte un error silencioso en uno visible.
- El fallback SQL multi-turno hereda los peores números (BIRD-Interact ≤17 % con GPT-5): conviene que el fallback trabaje sobre la pregunta reescrita a forma autocontenida (y mostrar la reescritura), no sobre el historial crudo.

### Gaps
- No encontré resultados 2025–2026 de CoSQL/SParC con modelos 7–8B genéricos ni de BIRD-Interact para modelos abiertos pequeños; tampoco el contenido de "Evaluating LLMs on Conversational Text-to-SQL under Chain Ambiguity and Intent Drift" ([arXiv 2608.29543](https://arxiv.org/pdf/2608.29543)) ni de "Memory Architectures for Multi-Turn Text-to-SQL" ([arXiv 2605.26394](https://arxiv.org/pdf/2605.26394)).
- Ningún estudio mide errores de arrastre de contexto en slot-filling determinista vs agente LLM sobre los mismos diálogos.

## 5. Errores en la generación de la respuesta tras una llamada/consulta correcta (fidelidad del resumen en lenguaje natural; números mal reportados) y mitigación

### Takeaway
No existe un benchmark específico que mida cuántas veces un LLM reporta mal números al narrar filas devueltas por SQL o por una API; la evidencia cercana (fidelidad en RAG/data-to-text, hallucinations tabulares en finanzas) muestra tasas no despreciables incluso en frontera (~6–7 % agregado en el mejor modelo de un leaderboard de fidelidad), y la mitigación consistente es sacar los números del LLM: cálculo y formato deterministas, renderizado estructurado, y LLM sólo para texto conector (o plantillas).

### Cited Findings
- Vectara FaithJudge (EMNLP 2025 Industry): leaderboard de fidelidad que incluye resumen, QA y data-to-text; el mejor en ese snapshot (gemini-2.5-pro) tuvo 6,65 % de tasa global de alucinación — [ACL 2025.emnlp-industry.54](https://aclanthology.org/2025.emnlp-industry.54/) [resumen]
- FaithBench (NAACL 2025): resúmenes de 10 LLMs de 8 familias anotados por humanos; las alucinaciones siguen siendo frecuentes y los detectores fallan a menudo — [ACL 2025.naacl-short.38](https://aclanthology.org/2025.naacl-short.38.pdf) [resumen]
- Resumen multi-documento: en promedio hasta 75 % del contenido generado es alucinado (tareas de noticias/conversaciones, no datos estructurados) — [Findings NAACL 2025](https://aclanthology.org/2025.findings-naacl.293/) [resumen]
- FAITH (finanzas, 2025): benchmark de alucinaciones intrínsecas sobre tablas de reportes anuales S&P 500 (lookup, comparaciones, cálculos multivariados); no se obtuvieron tasas por modelo — [arXiv 2508.05201](https://arxiv.org/pdf/2508.05201) [resumen]
- Estudio de resumen de noticias financieras: con filas tabulares crudas los LLM cometen errores de parseo y aritmética; la solución fue calcular en Python y que el modelo sólo redacte con los valores calculados — [arXiv 2608.19526](https://arxiv.org/pdf/2608.19526) [resumen; identificador/fecha a verificar]
- Anthropic: resolver identificadores técnicos (UUIDs) a lenguaje natural en la respuesta de la tool reduce alucinaciones en recuperación; `response_format` conciso/detallado; Programmatic Tool Calling evita que resultados intermedios entren al contexto — [Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents); [Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)
- Power BI Copilot "verified answers" muestra visuales aprobados (no texto generado) y Microsoft advierte que la salida de Copilot es no determinista — [Microsoft Learn](https://learn.microsoft.com/power-bi/create-reports/copilot-prepare-data-ai-verified-answers) [vendor]

### Inferences
- La etapa de redacción agrega un término de error multiplicativo a ambas arquitecturas: P(respuesta correcta) = P(datos correctos) × P(redacción fiel). Con frontera, el orden de magnitud del segundo término sería ~93–99 %; con un 8B Q4 y tablas de decenas de filas (conteos por carrera), es razonable esperar más errores (agregaciones mentales, omisión de filas, redondeos) — inferencia sin medición directa.
- Para "cero números inventados" el diseño dominante es: la tool/consulta devuelve ya el agregado; la respuesta se arma con plantilla en español ("Hay {n} pedidos en estado {estado}…") y la tabla se renderiza en UI desde el JSON, no desde texto del LLM. Un verificador post-hoc que extraiga cada número del texto y lo busque en el resultado es barato y atrapa el residuo.
- En A, el LLM suele recibir filas crudas y hacer él la agregación (contar, sumar, rankear) en su contexto: es exactamente el punto débil documentado (aritmética sobre tablas); en B la agregación vive en SQL certificado.

### Gaps
- No hay benchmark que mida la tasa de números mal reportados al narrar resultados SQL/API, ni con modelos 7–8B ni en español.
- No se obtuvieron tasas por modelo de FAITH ni la desagregación data-to-text de FaithJudge.

## 6. Comparaciones cabeza a cabeza (aunque parciales): agente API vs híbrido vs Text-to-SQL sobre las mismas preguntas

### Takeaway
Sólo hay comparaciones parciales de pares: API vs SQL sobre BIRD (Live API-Bench: las APIs resultan *más difíciles*, 7–47 % vs SQL), declarativo-SQL vs agente de tools sobre Spider+APIs (68,9 % vs 35,7 %), y capa semántica vs Text-to-SQL (dbt, Cube). No existe un estudio publicado que compare un agente con tools REST completas contra un híbrido router → consultas certificadas → SQL con abstención sobre las mismas preguntas midiendo respuestas incorrectas silenciosas. El único dataset que lo permitiría para Ars Docendi es el golden set propio (34/39 preguntas).

### Cited Findings
- Live API-Bench (EACL 2026): mismas preguntas BIRD expresadas como secuencias de API: 7–47 % de completitud (≈50 % con ReAct); los modelos "are sometimes able to exploit SQL better than APIs" y dependen de pistas semánticas en los nombres de tools — [arXiv 2506.11266](https://arxiv.org/abs/2506.11266); [ACL Anthology](https://aclanthology.org/2026.eacl-long.143/) [resumen]
- IBM declarativo (EMNLP 2025 Industry): un SQL único con APIs como tablas virtuales 68,9 % vs agente xLAM 35,7 % — [arXiv 2510.16470](https://arxiv.org/abs/2510.16470); [Lacuna](https://lacuna.tiptreesystems.com/work/declarative-techniques-for-nl-queries-over-heterogeneous-data/wrk_3ee74bff820bfdc00b59210380726a98) [resumen secundario]
- dbt 2026: capa semántica vs Text-to-SQL, 11 preguntas × 20 corridas: dentro de cobertura 100 % vs 62,5 %; fuera 0 % (error) vs 70 %; tras modelar 3 joins: 98,2 % vs 90,0 % (Sonnet 4.6) — [dbt Labs 2026](https://docs.getdbt.com/blog/semantic-layer-vs-text-to-sql-2026) [vendor]
- Cube 2026: 45,5–50,5 % → 67,7–68,7 % con documento semántico (forma contexto, no runtime) en Opus 4.7, Sonnet 4.6, GPT-5.4 — [arXiv 2604.25149](https://arxiv.org/abs/2604.25149) [vendor]
- Vercel d0 (de la ronda anterior): ~18 tools especializadas ≈ 80 % de éxito vs 1 tool bash sobre capa semántica Cube con Opus 4.5 ≈ 100 % (set chico, cifras secundarias) — [Vercel blog](https://vercel.com/blog/we-removed-80-percent-of-our-agents-tools) [vendor, resumen]
- Snowflake (interno): GPT-4o single-prompt ~51 %, Text-to-SQL dedicados ~79 %, Cortex Analyst (modelo semántico + verified queries) ~90 % — [VentureBeat](https://venturebeat.com/ai/snowflake-launches-cortex-analyst-an-agentic-ai-system-for-accurate-data-analytics) [vendor]

### Inferences
- Ordenando lo disponible por "respuestas incorrectas silenciosas" (no por exactitud bruta): (1) consultas certificadas/capa semántica runtime con abstención estructural fuera de cobertura (error ≈ router + slots); (2) agente con pocas tools gruesas tipo consulta estructurada (error ≈ selección + argumentos + composición cuando la pregunta no cabe en una llamada + redacción); (3) agente sobre muchos endpoints REST finos (compounding p^n, agregación en contexto); (4) Text-to-SQL libre sin abstención (~21 % de respuestas falsas en el set propio). El fallback SQL con abstención se ubica entre (2) y (4) según la agresividad del umbral.
- Con modelo frontera vía API (Claude), (2) se acerca a (1) dentro de cobertura, pero sigue sin abstención estructural: ante una pregunta fuera de la superficie, el agente compone o aproxima en lugar de negarse. Con 8B local, la distancia entre (1) y (2) es mucho mayor (miss_param, ComplexFuncBench 5 %, ToolHop 10–16 %).
- Recomendación de medición (inferencia): evaluar ambas arquitecturas sobre el mismo golden set de Ars Docendi registrando por pregunta {correcta, incorrecta, abstención}, separando single-turn y follow-ups, y reportar riesgo selectivo (incorrectas / contestadas) además de exactitud, con ≥4 corridas por pregunta para medir pass^k.

### Gaps
- No existe estudio cabeza a cabeza A vs B vs Text-to-SQL con el mismo modelo y mismas preguntas midiendo respuestas incorrectas silenciosas; tampoco con modelos locales 8–14B ni en español.
- No pude extraer las cifras por modelo de Live API-Bench para comparar con BIRD-SQL del mismo modelo.
