## Context

See `proposal.md` for motivation. This section only covers the current state that shapes _how_ to build A1–A5.

- **The 4-state contract is closed by design.** `ResultadoDelTurno.EstadoDelTurno` is `{ Respondida, NoContestable, NecesitaAclaracion, ServicioDegradado, Fallo }` (`Fallo` never leaves the process). The domain doc treats "four states, no more" as a deliberate invariant ("Decisiones registradas"). `DisponibilidadDelModelo.MotivoSinModelo { Ninguno, CuotaAgotada, ProveedorCaido }`, consulted once in `CapaConversacional.ResolverAsync`, is the existing extension point that lets a _reason_ vary while the _wire state_ stays `ServicioDegradado`.
- **Quota today**: `CuotaEnMemoria` counts model _calls_ (not turns) in a sliding window, in a process-local `Dictionary<Guid, Queue<Consumo>>` guarded by a plain lock. Checked before the pipeline starts; charged unconditionally in `CapaConversacional`'s outer `finally`, after the pipeline runs, regardless of outcome — this is deliberate today ("a turn that falls over still pays for what it spent") and this change keeps that spirit but changes the _unit_.
- **No existing per-actor concurrency guard.** Grepping `Modules.Asistente` for locks/semaphores/advisory finds only unrelated in-process locks (`CuotaEnMemoria`, `AlmacenDeHilosEnMemoria`, `BreakerDelProveedor`, `IdempotenciaEnMemoria`) and a lazy-init semaphore. A3 is new ground, and the frontend's "one turn at a time" guard (`useAsistente`) is a client-side courtesy, not a server-side control — it does not stop two tabs, two devices, or a retried request from reaching the backend concurrently.
- **`asistente` schema is already denied wholesale** to both read-only roles (`REVOKE ALL ON SCHEMA asistente`, declared in `002_asistente_registros.sql`). A new table created under this schema is unreachable by either read-only role with **no new manifest entry and no new `GRANT`** — Postgres denies by default, and the schema-level revoke blocks even `USAGE`. This is confirmed by `manifiesto-privilegios.json`'s own description of why `asistente` is `"denegado"` at the schema level.
- **The purge mechanism (`PurgaDeRegistros`) already sweeps four independently-windowed tables** (`registro_operativo` 90d, `registro_analitico` 90d by day, `hilo_historico` 180d by `ultima_actividad`, `auditoria_acceso_historial` 365d), each cut against `TimeProvider`, logged and never fatal. Adding a fifth sweep for the new admin-audit table is additive, not a new mechanism.
- **`asistente.consultar` / `asistente.ver_consulta` / `asistente.leer_historial_ajeno` were all seeded from `database/identity/`, never from `database/asistente/`** — per AGENTS.md rule 4, only the identity-owning migrations write `identity.permisos`/`identity.rol_permisos`, even for a permission that exists to gate the assistant. Confirmed pattern: `INSERT INTO identity.permisos (id, code, nombre, descripcion) VALUES ('b2000000-...', code, ...) ON CONFLICT (code) DO NOTHING;`, plus a `DO $$` guard that raises if any of the seven system roles has no explicit grant/deny decision recorded for the new permission.
- **UUID/migration numbering is a real collision risk, with precedent.** `011_identity_permiso_asistente.sql` documents an actual `23505` collision from two branches picking the same next-free UUID off the same base migration. Checked now: local `database/identity/` goes up to `019_identity_permiso_leer_historial_ajeno.sql`, highest seeded UUID is `...028`; `origin/develop` only has through `011_identity_permisos_pantallas.sql` (everything from `011_identity_permiso_asistente.sql` onward is still local/unmerged feature-branch work, including the two in-flight sibling changes). So **today** the next free slot is migration `020`, UUID `b2000000-0000-4000-8000-000000000029` — but per the documented lesson, this must be re-checked against `origin/develop`'s actual state immediately before this change is implemented, not trusted from this planning pass.
- **`database/asistente/` locally has `001`–`005`** (grants, registros, retroalimentacion, historial, auditoria_soporte); `origin/develop` has none of these yet either (all still local/unmerged). Next free number today is `006`.
- **Display-name resolution already has a seam.** `ArsDocendi.Shared.Identity.IConsultasIdentity` exposes `ListarUsuariosAsync()` — its own doc comment says it exists "para resolver actores en respuestas de auditoría" — and `ObtenerPersonaAsync`. This is the same seam every other module already uses to read identity (rule 4), and is unrelated to `GET /api/administracion/usuarios` (`usuarios.ver`), which is a `Modules.Administracion` HTTP endpoint, not a Shared read seam.

## Goals / Non-Goals

**Goals:**

- Fit every new blocked outcome (own quota, org cap, concurrent turn, maintenance) into the existing 4-state contract by reusing `ServicioDegradado` with a distinguishing reason — never a 5th state, never an HTTP 500.
- Make the budget, the kill switch, and the admin audit trail live in Postgres, inside the `asistente` schema, denied to both read-only roles by the same schema-level mechanism that already denies the rest of the module's own tables.
- Keep every new admin surface gated by one new permission, seeded the same way the module's three existing permissions were seeded.

**Non-Goals:**

- Archiving/reconciling `asistente-cuota`, `asistente-contrato-de-respuesta`, or `asistente-capacidades` into `openspec/specs/` — they are still unarchived from earlier changes; this change adds new capabilities alongside them and documents the relationship (Decision D9), but does not run `opsx:archive`.
- Any Azure dependency. The kill switch is designed to be _replaceable_ by Azure App Configuration later (Decision D7), but nothing Azure-related is added now.
- A notification/email system. TD-013 stays closed as written; thresholds surface only in the dashboard and a structured log warning.
- Changing how the SQL lane, the masking layer, or the read-only roles' privileges work. This change only adds tables the assistant's own read-only roles must keep being unable to read.

## Decisions

### D1 — New blocked outcomes reuse `ServicioDegradado`; no 5th wire state

`DisponibilidadDelModelo.MotivoSinModelo` gains three values — `TopeOrganizacionalAgotado`, `TurnoConcurrente`, `Mantenimiento` — alongside the existing `CuotaAgotada`/`ProveedorCaido`. All five continue to map to `EstadoDelTurno.ServicioDegradado` at the HTTP boundary, each with its own text via `PoliticaDeAbstencion`. **Alternative considered**: a dedicated 5th (or 8th) state per new reason. Rejected — the domain doc treats the four-state count as load-bearing ("el carril es un servicio... antes de tener los cuatro estados"), and every new reason here is semantically "you cannot get an answer from the model right now," which is exactly what `ServicioDegradado` already means to the client.

### D2 — Quota unit changes from model-calls/sliding-window to turns/calendar-day

The per-user quota moves from counting model _calls_ in a sliding window to counting _turns_ on a fixed calendar day, because turns/day is what a non-technical admin can reason about and set without knowing the pipeline's call fan-out, and because a persisted budget needs a stable, auditable period boundary — a sliding window recomputed against `now()` on every check is a worse fit for a value an admin edits and expects to "reset at midnight." The calendar-day boundary is UTC midnight, matching the `TimeProvider`-based UTC handling `PurgaDeRegistros` and the rest of the module already use throughout — introducing a second, institution-local notion of "day" would be a new concept for this one feature alone. A turn still only counts if it invoked the model at least once (matching the existing rule that a turn resolved without the model — a greeting, a recognized menu answer — spends nothing), and it counts exactly once regardless of how many model calls that turn made internally (rewrite + generate + retry + draft is still one turn). **Alternative considered**: keep counting model calls, just persist the same sliding window. Rejected per the task's own framing — a persisted budget is meant to be admin-legible, and "60 calls per 60 minutes" is not.

### D3 — Org-wide cap in estimated USD/month, user quota in turns/day

Two different units for two different questions: the per-user quota answers "is this person using it fairly relative to their peers," where turns are legible and the actual token cost per turn is roughly comparable across users asking ordinary questions. The org-wide cap answers "are we about to get an unexpected bill," where the actual cost driver is tokens × price, not turn count — two providers or two models at different verbosity make turns a poor proxy for spend. **Alternative considered**: both limits in the same unit (either both turns, or both USD). Rejected — forcing the per-user quota into USD would require every admin to think in provider pricing to set a fair per-person limit, and forcing the org cap into turns would make it silently wrong the moment the provider or model changes.

### D4 — Charging semantics: one turn, charged once, only if the model was invoked, even on failure

A turn is charged against the daily quota exactly once, in the same outer `finally` that already exists in `CapaConversacional`, if and only if the pipeline reached at least one provider call. A turn blocked _before_ the pipeline starts (own quota exhausted, org cap reached, concurrent turn detected, maintenance active) is never charged — it never got as far as spending anything. A turn that fails or times out _after_ calling the model is charged, exactly like today, because the resource was consumed regardless of the outcome. This preserves the existing invariant from `asistente-cuota` ("a turn resolved without the model does not spend quota") while changing what "spend" is denominated in.

### D5 — One-in-flight-turn lock: Postgres advisory lock, not an in-process lock

**Chosen**: a session-level Postgres advisory lock (`pg_try_advisory_lock(hashtext('asistente:turno:' || actor_id))`), acquired on a dedicated connection at the very start of the turn (before the quota/maintenance/org-cap checks, since it is the cheapest check and the one most likely to reject instantly), and released (`pg_advisory_unlock` + connection disposal) in the same outer `finally` that already handles quota charging.

**Why not an in-process lock** (e.g. a `ConcurrentDictionary<Guid, object>` or `SemaphoreSlim` per actor, the pattern already used by `CuotaEnMemoria`/`AlmacenDeHilosEnMemoria`): it only protects one process. The Host can run more than one instance (rolling redeploys, and this is explicitly a stated concern for the shared Anthropic rate limit and the future single-GPU local model), and an in-process lock gives each instance its own, independent notion of "in flight" — two instances would each let the same actor's turn through, defeating the purpose.

**Why a session-level lock and not `pg_try_advisory_xact_lock`**: a transaction-scoped advisory lock would require holding one transaction (and one connection) open for the full 150 s turn budget, on the connection pool shared with everything else the request does — at ~30 concurrent users that is a meaningful, avoidable hold on pool capacity, and it would couple the lock's lifetime to whichever single connection/transaction happens to run it, when the turn's own SQL lane already opens and closes its own short-lived `READ ONLY` transactions independently. A session-level lock on its own dedicated connection decouples the two: the lock's connection does nothing else and is cheap to hold.

**Leak risk, and its mitigation**: a session-level advisory lock is _not_ released when a pooled connection is `Close()`d back to the pool — Postgres only releases it when the underlying backend session actually ends. If code forgot to call `pg_advisory_unlock` before disposing the connection, the lock would leak to whoever the pool hands that physical connection to next. Mitigated by: (a) the same `try/finally` discipline this module already applies everywhere else (`PresupuestoDelTurno`, `IdempotenciaEnMemoria`), making release unconditional; (b) a dedicated connection for the lock, so it is never accidentally reused for other queries while held; (c) crash safety is preserved regardless of the pool, because a process crash drops every one of that process's physical connections' TCP sockets, and Postgres releases all of a backend's session-level advisory locks the moment it detects the socket is gone — so "the instance died mid-turn" cannot leave the actor permanently locked out, only "a code bug forgot to unlock while the process kept running" can, and that is caught the same way any other missing-`finally` bug would be.

### D6 — Price table: versioned by effective date range, joined at read time for the dashboard, accumulated incrementally for the org cap

A price-table row is `(proveedor, modelo, vigente_desde, vigente_hasta nullable, precio_por_1k_entrada, precio_por_1k_salida, precio_por_1k_cache, moneda)`. Publishing a new price closes the previous row's `vigente_hasta` and opens a new one — history is never edited in place. The usage dashboard (A1) computes a turn's estimated cost by joining its tokens against the price-table row whose validity range contains `registro_operativo.ocurrido_en`, so a later price change never rewrites an earlier estimate. The org-wide monthly cap (A2) does **not** re-run that join on every turn to check the cap; it maintains a running per-month accumulator incremented once, at charge time, using whatever price is effective _then_ — which is by construction the same price that would later be looked up for that turn's historical range, so the two mechanisms never disagree, they just compute the same number at different times for different purposes (one incrementally for a cheap threshold check, one on demand for the dashboard).

### D7 — Maintenance flag behind a swappable abstraction; Postgres-backed default, no Azure now

A small port (`IInterruptorDeMantenimiento`, or similar) exposes "is maintenance active, and why" plus "activate/deactivate, with actor and reason." The default implementation reads/writes a single-row `asistente.mantenimiento` table. Nothing Azure-related is referenced anywhere — the abstraction exists so that swapping the default implementation for one backed by Azure App Configuration later is a new class and a composition change, the same shape this module already uses for swapping model providers, never a change to any caller.

### D8 — Admin bypass is scoped to maintenance mode only

An actor with `asistente.administrar` can still submit turns while maintenance is active (to verify recovery before reopening to everyone), but is **not** exempt from their own per-user quota, the org-wide cap, or the one-turn-in-flight rule. Maintenance mode is an availability switch meant to be bypassed for verification; quota and concurrency exist to protect a shared rate limit and a shared budget, which an admin's test turns still consume and still risk, exactly like anyone else's.

### D9 — Relationship to the still-unarchived `asistente-cuota` / `asistente-contrato-de-respuesta` / `asistente-capacidades`

`openspec/specs/` has zero `asistente-*` capabilities today — every one of them, including the three above, still lives only inside their originating (already "✓ Complete" but unarchived) change folders. A `MODIFIED` delta needs a base spec under `openspec/specs/` to modify; none exists, so this change cannot file one. Per the task's own instruction, this change instead adds new capabilities (`asistente-presupuesto-persistente`, etc.) that are self-contained and internally consistent with the _behavior_ those unarchived capabilities describe (same 4-state contract, same "no call, no charge" spirit), without formally modifying their text. **Follow-up, out of scope here**: when `asistente-presupuesto-degradacion` and this change are both archived, `asistente-cuota`'s requirements ("measured in model calls, sliding window") and `asistente-presupuesto-persistente`'s ("measured in turns, calendar day") describe the _same_ enforcement point with different units — that reconciliation (most likely: `asistente-presupuesto-persistente` supersedes and replaces `asistente-cuota` at archive time) should happen at `opsx:archive` time, not be guessed at here.

### D10 — TD-011 is reopened and updated, not silently closed

TD-011 was accepted in-memory because there was no evidence of abuse, with an explicit note that persisting it would require "a table on the hot path of every call, with its own retention of indirect personal data." That is exactly what this change does — the justification changes from "no evidence of abuse yet" to "admin cost control under ~30 concurrent real users," which is the condition TD-011 itself named as the trigger to revisit. `docs/quality/tech-debt.md` gets TD-011's remediation column updated to point at this change (not deleted — the historical reasoning stays legible), and a note that the circuit-breaker's in-memory state is _not_ addressed here (still process-local, still out of scope, unless real abuse or repeated breaker-state loss across redeploys becomes evidence for a follow-up).

### D11 — Retention per new table

- `asistente.tabla_precios`, role defaults, and per-user overrides: no purge — low volume (a handful of rows per provider/model change or per admin edit), and prices must stay available indefinitely to price historical `registro_operativo` rows correctly (D6).
- `asistente.consumo_diario_actor` / `asistente.consumo_mensual_organizacion`: swept by the existing `PurgaDeRegistros`, same 90-day window as `registro_operativo`, since they are derived counters over the same underlying activity.
- `asistente.auditoria_administracion`: its own independent retention window (default 365 days, matching the precedent set by `auditoria_acceso_historial`), swept by the same purge mechanism, because — same reasoning already established for that precedent — an audit record's usefulness outlives the thing it describes (a budget override can be changed again; the record that it was once set to some value should not disappear just because the override moved on).

### D12 — Display names resolved via `IConsultasIdentity`, not via `usuarios.ver`

The dashboard resolves `registro_operativo.actor_id` to a human-readable name through `ArsDocendi.Shared.Identity.IConsultasIdentity` (`ListarUsuariosAsync`/`ObtenerPersonaAsync`) — the same cross-cutting identity-read seam every module already uses per rule 4, and one whose own doc comment names exactly this use case ("resolver actores en respuestas de auditoría"). This resolves the gap the proposal flagged: an admin with `asistente.administrar` does **not** also need `usuarios.ver`, and the dashboard does not call `GET /api/administracion/usuarios` or duplicate a module-owned SQL lookup. The support-history screen's `SelectorDeSujeto` keeps using its existing `usuarios.ver`-gated endpoint unchanged — that screen needs to _search_ people to pick one, a materially different need from resolving already-known `actor_id`s in a results table.

### D13 — New permission `asistente.administrar`, seeded to `sys_admin` only

Follows the exact pattern of `asistente.consultar`/`asistente.ver_consulta`/`asistente.leer_historial_ajeno`: seeded from `database/identity/`, a fixed UUID, `ON CONFLICT (code) DO NOTHING`, plus the same guard that raises if any of the seven system roles has no explicit decision. Unlike the other two module permissions (seeded to _nobody_, not even `sys_admin`, because they gate diagnostic/support surfaces reachable by anyone once granted), `asistente.administrar` is seeded directly to `sys_admin`: budgets and the kill switch are operational controls over the whole module's availability and spend, not personal-data-adjacent diagnostic surfaces, and `sys_admin` is the role the system already reserves for exactly this kind of cross-cutting operational control (it is `NOINHERIT` and grants nothing on its own until assigned — assigning it to a person is already the explicit, deliberate step the other two permissions' migrations describe as the model to follow, just via role assignment instead of a later `/membresia-roles` grant). **Important caveat, reconfirmed at implementation time, not trusted from this planning pass**: the next free identity migration number and permission UUID must be re-derived from `origin/develop` immediately before implementing, because — as `011_identity_permiso_asistente.sql` documents from a real past collision — two branches picking the same "next free" slot off the same base produces a primary-key collision at merge time, not at review time.

## Risks / Trade-offs

- **[Risk] The advisory-lock connection is one more connection held per in-flight turn** → Mitigation: it is a plain `pg_try_advisory_lock` round-trip plus an idle hold, not a transaction; at ~30 users the additional pool pressure is small, and it is explicitly _not_ shared with the SQL lane's own transactions (D5).
- **[Risk] A price-table gap (a provider/model combination with no matching row) silently reports zero cost** → Mitigation: the dashboard requirement explicitly calls this out as "not priced" rather than defaulting to zero, so a missing price is visible as a gap, not a false all-clear.
- **[Risk] Reconciling this change's turn-based quota with the older call-based `asistente-cuota` capability is deferred** → Mitigation: explicitly named as a follow-up at archive time (D9), not silently dropped.
- **[Trade-off] The org cap and the per-user quota use different units** → Accepted per D3; the alternative (one unit for both) makes one of the two limits materially harder for an admin to reason about.

## Migration Plan

1. `database/identity/020_identity_permiso_administrar.sql` — seed `asistente.administrar` (UUID and exact number reconfirmed against `origin/develop` at implementation time per D13), grant to `sys_admin` only, with the seven-system-roles decision guard.
2. `database/asistente/006_asistente_administracion.sql` — all seven new tables in one migration, the same way `002_asistente_registros.sql` created its two registries together: `presupuesto_rol` (role defaults), `presupuesto_usuario` (per-user overrides), `tope_organizacional` (the org-wide monthly USD cap), `consumo_organizacional_mensual` (its running accumulator), `tabla_de_precios` (D6's versioned price table), `modo_mantenimiento` (D7's single-row flag), and `auditoria_administracion` (D11's append-only trail).
3. Backend: extend `MotivoSinModelo`, replace `ICuotaDelActor`'s implementation (remove `CuotaEnMemoria`), add the advisory-lock component (D5), the maintenance abstraction + default implementation (D7), the price-table reader (D6), and the new controller surface (dashboard reads, budget edits, maintenance toggle) gated by `asistente.administrar`. Extend `CapacidadesDto` and `PurgaDeRegistros`.
4. Frontend: extend `useAccesoAlAsistente`/`CapacidadesDelAsistente`, add the quota/maintenance indicator to the status strip, add the new gated admin route.
5. Docs in the same diff (AGENTS.md rule 6): `docs/architecture/domains/asistente.md`, module `README.md`, `docs/architecture/api-contracts.md`, `docs/architecture/data-model.md`, `docs/business-rules/asistente.md` (BR-`asistente`-007 onward), `docs/product/designs/asistente-conversacional-design-spec.md`, `docs/quality/tech-debt.md` (TD-011 update).

**Rollback**: every new table is additive and net-new; dropping them and reverting `ICuotaDelActor` to `CuotaEnMemoria` is a clean revert with no data dependency from existing tables onto the new ones. The one non-trivial rollback step is the permission migration — per rule 4's convention, permission migrations are additive and idempotent (`ON CONFLICT DO NOTHING`) and are not rolled back by dropping the row; an unwanted grant is revoked the same way any other permission is revoked (`/membresia-roles` or a follow-up migration), not by editing migration history.
